### 1.2. Известные числа, на которые опирается дизайн

- **Шум собственной арифметики** (контрольные пары одинаковой арифметики, этап 8 третьего круга): **ΔNLL 0,003–0,005** — это *пол*, ниже которого любой допуск `δ_NLL` бессмыслен.
- **Vision-продолжение (Б1, точные замеры 2026-11-19):** на общих шагах `0..3` `common_max_logit_delta = 0.513805`, `common_max_KL_temperature1 = 0.001963`; жадный argmax переворачивается на почти равной паре (зазоры `0.030472`/`0.070221`). Все оракулы состояния точные. Это **не дефект**, а неэквивалентность decode- и prefill-арифметики MoE (диапазон `0.09–0.82` логита из INVESTIGATION_RESULT §В).
- **Расчёт стоимости (stage8), исправлено по замечанию владельца:** `0,003–0,005` — это **средний шум контрольных пар** (floor допуска), а **междокументный разброс** парных `ΔNLL` составляет **`σ = 0,0147`**. Планирование объёма ведётся от `σ`, а не от среднего шума: при истинном сдвиге кандидата `+0,0046` и границе `δ = 0,010` (разрыв `δ − 0,0046 = 0,0054`) для мощности 90 % при `α = 0,025` нужно **~78 документов на ячейку** (ориентир владельца ~77); при плановой мощности 80 % — 59 при `α = 0,025` и 46 при `α = 0,05`. Планируем с запасом **~80 документов на ячейку**; точное N каждой ячейки замораживается после pilot'а по оценке `σ` и расчёту мощности.
- **`T15 sparse`:** `GUFO_QWEN_SPARSE_ATTN=1` влияет на decode только после порога `sparse_min_context = 8192`, а фактическое начало прореживания — **290 блоков = 18 560 токенов**. Значит, прикладной набор обязан содержать задачи с историями **строго > 18 560 токенов** (цель 20K–64K), иначе sparse-кандидат будет неотличим от базового FP16.
- **Крупный текст 48–96 pt:** известное свойство весов/проектора (воспроизводится в llama.cpp), не дефект движка. В наборе выделяется отдельной группой с семантикой `known_limit`, чтобы не маскировать и не смешивать с обычным OCR.

## 2. Принципы дизайна

1. **Ничего существующего не ломаем.** `faex2_quality.jsonl`, `faex2_acceptance.py b2`, `test_faex2_fixtures.py` остаются байт-в-байт; новый набор — новые файлы и отдельная команда раннера.
2. **Только синтетика и stdlib.** Все тексты, таблицы и изображения генерируются детерминированно кодом (как `faex2_images.py`/`faex2_remediation_images.py`); никаких личных данных. SHA-256 эталонов закрепляется CPU-тестами.
3. **Две скорости оценки.** Автопроверки (точные `expected_values`, JSON-схемы, числовые ответы, извлечение фактов) исполняются кодом; рубрики — человеком, но только через слепые пары.
4. **Каждая задача — воспроизводимый артефакт.** Фиксированные параметры, отсутствие зависимости от сети/даты/случайности (где нужен seed — он зашит и записан), manifest с SHA-256.
5. **Sparse-набор обязателен.** Домен D длинного контекста — не «желательно», а обязательное условие применимости набора к `T15`.
6. **Пороги Q1 — от шума и мощности, а не от удобства.** Каждый допуск сопровождается обоснованием: во сколько раз выше шума арифметики, сколько документов/задач нужно для мощности, сколько GPU-часов стоит.

  - `vision-multi` (2, `auto`): два изображения с содержательным текстом в одном запросе, вопрос о порядке;
  - `big-text-known-limit` (2, `known_limit`): крупный текст 48–96 pt — **отдельная группа с семантикой `known_limit`**, как в `run_probe`: неверный ответ → `KNOWN_LIMIT_FAIL`, не FAIL и не PASS. Это явно учитывает свойство из DESIGN §4, не маскирует его и отделяет от обычного OCR.
- **C (20; 12 коротких, 8 средних).** Подгруппы:
  - `code-fix` (6, `auto`, короткие): фрагмент Python 10–25 строк с одной детерминированной ошибкой (off-by-one, неверная сортировка, потеря края диапазона); автопроверка — точный исправленный вывод;
  - `code-explain` (4, короткие): 2 `auto` (возвращаемое значение функции на фиксированном входе) + 2 `manual` (объяснение по рубрике);
  - `tool-chain` (6, `auto`, средние): 2–3-шаговые tool-call сценарии по схемам `hermes_synth` (`search → open`, `ls → read → edit`), с фиксированными `tool_result`-литералами и проверкой финального ответа;
  - `json-schema` (2, `auto`, короткие): structured output с проверкой схемы и значений (расширение шаблона `json-schema` из `faex2_cases.jsonl`);
  - `hermes-reuse` (2, `auto`, средние): 2 выбранных случая `hermes_synth` (1 `tool` + 1 `mixed`) включаются как есть через `hermes_synth.build_request` — связка с реальным профилем Hermes Agent; полный набор 15 случаев остаётся доступен отдельным раннерам (`dflash2_eval.py`).
- **D (28, все > 18 560 токенов; 14 × 20K–32K, 14 × 44K–64K) — обязателен для `T15 sparse`.** Детерминированно:
  - `long-retell` (8, `manual`; 4 + 4 по диапазонам): синтетический документ — «справочник/дневник наблюдений» из повторяемых секций с ~20 уникальными фактами; вопрос — пересказ/извлечение, оценка по рубрике;
  - `long-facts` (12, `auto`; по 6 на диапазон): тот же класс документов, вопрос указывает на факт в **начале / середине / конце** документа (по 2 позиции на диапазон) — прямая проверка того, что sparse-прореживание не теряет удалённые блоки;

Задачи, не дотянувшие до порога, в отчёте помечаются `SHORT_OF_SPARSE_THRESHOLD` (не PASS).

### 3.2. Автопроверки и рубрики

Каждая задача несёт:

```json
{
  "id": "ocr-table-schedule-01",
  "domain": "ocr-table",
  "bucket": "short",
  "images": ["appset:table/schedule_a"],
  "prompt": "…",
  "max_completion_tokens": 512,
  "autocheck": {"type": "contains_all", "values": ["9:00", "17:00"]},
  "expected_values": {"rows": 5, "total": 1240},
  "evaluation": "auto|manual|known_limit",
  "critical_failures": ["incorrect_math", "incorrect_fact", "fabricated_source", "empty", "truncated"],
  "pass_criteria": { "…": "как в существующей рубрике" }
}
```

- **`auto`**: автопроверка исполняется раннером (`contains_all`, `exact`, `excludes_all`, `json_schema`, `numeric_within`, `sentence_count`, `regex`), результат — `PASS`/`FAIL` без человека. Автопроверками покрыты **66 из 96** задач (все подгруппы B, кроме `known_limit`, все `code-fix`/`tool-chain`/`json-schema`/`hermes-reuse`, `long-facts`, `long-tool-dialog`, `long-vision-dialog` и 6 новых задач A).
- **`manual`**: свободные объяснения (28 задач: A, часть C, `long-retell`) — рубрика из 4 измерений `correctness/instruction/russian_clarity/explanation` **в точности как в `faex2_quality.jsonl`** (якоря 0/1/2, `pass_criteria`: `correctness == 2`, каждый ≥ 1, сумма ≥ 6, `critical_failure_result: FAIL`). Переиспользование той же рубрики позволяет одному рецензенту читать оба набора одинаково и не ломает `QualityFixtureTests`. Для задачного барьера greedy-прохода (§5.2) `manual`-задачи оцениваются по этой же рубрике **слепо**, но на greedy-ответах — иначе знаменатель 94 не достигается (см. §5.2).
- **`known_limit`**: только группа `big-text-known-limit` (2); семантика наследуется от `run_probe` (неверный ответ → `KNOWN_LIMIT_FAIL`, итог отчёта `KNOWN_FAILURES`, неожиданный pass → `unexpected_probe_passes`). Эти 2 задачи исключены из PASS/FAIL-статистики барьеров.
- **Критические отказы** (`empty`, `truncated`, `incorrect_math`, `incorrect_fact`, `fabricated_source`) переопределяют любой балл — как сейчас; проверяются и в auto-, и в manual-задачах.

### 3.3. Протокол слепого парного чтения

Новая команда раннера `export-blind`:

1. Берёт два каталога прогона (вариант X и вариант Y) по одному и тому же набору.
2. Для каждой задачи формирует пару ответов; порядок A/B внутри пары перемешивается **детерминированно** (seed `20261119` в manifest, но сам файл маппинга `blinding_key.json` — имя задачи → вариант — пишется в отдельный файл, который рецензенту не показывается).
3. Пишет `blind_pairs.jsonl` — **в записи есть всё необходимое для оценки**: `pair_id`, `task_class` (domain+bucket, для выбора рубрики), `prompt` (или `messages` диалога), `images` (ссылки на файлы изображений, выгружаемые рядом), `expected_facts`, `prohibited_errors`, `expected_values`, `rubric`, `response_a`, `response_b`. **Скрываются только `id` задачи и метка варианта X/Y** — без промпта и эталонов рецензент оценить ответ не может.
4. Рецензент пишет `review_record` (`scores`/`rationale`/`critical_failures`) в `blind_reviews.jsonl`.
5. Команда `unblind` соединяет отзывы с маппингом и печатает парные исходы `both_ok / only_X / only_Y / both_fail` и доли дискордантных пар по доменам — без права менять отзывы после раскрытия.

Правила: первичны **greedy-прогоны** (temperature 0) — они питают детерминированный задачный барьер (§5.2) и автопроверки; параллельно делается **ровно один sampled-проход** (production sampler: temperature 1, top_k 20, top_p 0,95, min_p 0,05, seed фиксирован в manifest) — его ответы идут в слепое чтение, потому что при greedy обе стороны часто совпадают байт-в-байт и чтение не даёт информации. Решение владельца (2026-11-19): **1 sampled-проход, без второго прогона** — ради бюджета; дисперсия temperature = 1 учитывается статистикой парной разности (§5.2), а не повторами.

### 3.4. Политика `enable_thinking` и `cache_prompt` (по подгруппам)

Не копируем `enable_thinking: False` из `faex2_acceptance.chat_request` туда, где проверяется рабочий профиль Hermes/рассуждений:

| Подгруппы | `enable_thinking` | Бюджет рассуждения | `cache_prompt` |
|---|---|---|---|
| A (все), B (все, включая `big-text`), `code-fix`, `code-explain`, `json-schema`, `long-facts`, `long-retell` | **false** (`chat_template_kwargs`) | — | `false` — свежий prefill, детерминированные счётчики |
| `tool-chain`, `long-tool-dialog`, `long-vision-dialog` | **on** (рабочий профиль Hermes) | серверный 512 | ход 1 — `false`; ходы 2+ — `true` (реалистичный диалог и проверка переиспользования префикса) |
| `hermes-reuse` | **как в фикстуре** (`base_request.json`, `reasoning_effort: medium`) — запрос строится `hermes_synth.build_request` без переопределений | из фикстуры | как в фикстуре |

Правило простое: точечные задачи с эталоном и автопроверкой идут без рассуждений (короткий детерминированный ответ); всё, что моделирует многошагового агента Hermes, — с его рабочим профилем рассуждений. Политика фиксируется в manifest прогона и проверяется тестами.

## 5. Контракт `Q1`: проект на утверждение

Заменяет §4–§7 черновика 2026-11-13 в части чисел и объёмов. Ключевой сдвиг: **двухуровневая структура** — точные инварианты (без допусков) и барьеры приближений (численные/задачные), плюс явная судьба каждой проверки.

### 5.1. Уровень 1 — точные инварианты (без допусков, не ослабляются ни при каких Q-контрактах)

1. `exact restore` / `append_max_logit_error = 0.00` — восстановление снимка на точной границе даёт побитно те же логиты.
2. Побитная повторяемость decode: тот же вход → тот же выход (одиночный и пакетный decode).
3. MTP verify/rollback/commit — точные; `cached_trajectory_matches_serving = 1`.
4. Побитная чанк-инвариантность матричного prefill.
5. **100 % валидность tools/JSON** (имя инструмента, аргументы по схеме, `finish_reason`, structured output) на всём наборе — любое нарушение = FAIL кандидата независимо от скорости.
6. `empty`/`truncated` ответы, смешивание сессий, потеря истории — FAIL без статистического допуска.

### 5.2. Уровень 2 — барьеры приближений

Применяются к каждому приближению: `prefill` (P vs G1), `vision continuation`, `GUFO_QWEN_SPARSE_ATTN=1`, условный `Q8_0` KV, `Q6_K`. Для каждого кандидата — свой manifest и свои пары, но барьеры одни.

**Численные барьеры (teacher-forced, `logits-nll-report.py` + его доработка — §6, п. 0):**

| Параметр | Предложение | Обоснование |
|---|---:|---|

**Барьер vision:**
- `exact restore` — уровень 1, без допусков.
- `cold-prefill` и vision-часть набора: новые синтетические изображения (§3.1 B) с эталонами, автопроверки + рубрика; численный барьер — те же δ_NLL/κ по vision-срезу (эмбеддинги изображения фиксированы, сравниваются текстовые логиты после изображения).
- Группа `big-text-known-limit` **исключена** из PASS/FAIL-статистики (семантика `known_limit`); её неожиданные успехи фиксируются как `unexpected_probe_passes`. Проверка опционального даунскейла крупного текста — отдельная задача после Этапа 1 (как в ROADMAP §Этап 1 п. 3), не часть Q1.

### 5.3. Почему эти пороги честные

- Они **выше среднего шума арифметики** (0,003–0,005), поэтому контрольная пара их проходит — контракт не строже собственной погрешности метода (главный дефект старого черновика). Объём при этом честно считается от **междокументного разброса `σ = 0,0147`**, а не от среднего шума — поэтому документов нужно ~80 на ячейку, а не «дюжина».
- Они **ниже наблюдённых эффектов** реальных различий путей: `common_max_logit_delta = 0.513805` и переворот argmax при KL 0,001963 показывают, что «почти нулевые» отличия распределений реально меняют жадный текст; допуск 0,010/0,020 не маскирует такие эффекты в задачном барьере — его ловит именно прикладной набор и критические отказы.
- Объёмы **исполнимы на одном узле**: ~560 документов численного среза и 96 задач на пару кандидатов — при условии, что **scalar `G1` читается один раз на замороженный корпус** (расход амортизируется между всеми кандидатами), а для пар `sparse` обе стороны — быстрые пути (FP16 и sparse), без scalar-чтения. Итоговые GPU-часы фиксируются по таймингам pilot'а (§5.5), а не оценкой на глаз.
- Каждое число помечено в §5.7 статусом; решения владельца от 2026-11-19 зафиксированы, финальные объёмы/лимиты — после pilot'а.

### 5.4. Статистика (сокращённо относительно черновика)

- Единица bootstrap — документ/семейство задач; парные интервалы; α = 0,05 односторонний для PASS-стороны.
- Семейство K = 6–8 ячеек (3 домена × 2 длины + задачный барьер + sparse-барьер); поправка Bonferroni `α/(2K)` — только для одновременно публикуемых двусторонних границ; для одного решения «все барьеры выполнены» — intersection-union без поправки (как в черновике).
- Совместная плановая мощность **≥ 80 %** при альтернативах «потерь нет, ΔNLL = κ/2» — снижено с 90 % черновика, потому что семейство K и объёмы теперь соответствуют одному узлу; расчёт мощности — по pilot до заморозки manifest. Если 80 % недостижимо — `INCONCLUSIVE`, объём не добирается после раскрытия.

### 5.5. Бюджет GPU-часов (один узел `faex2`, окна только с согласия владельца)

| Этап | Объём | Оценка | Лимит |
|---|---|---|---:|
| Pilot прикладного набора | 96 задач × 1 вариант (база) + тайминги | короткие ~20 с, длинные ~2–4 мин | **2 GPU-ч** |
| Парный прогон набора | 96 × 2 варианта × (greedy + 1 sampled) | ≈ 4–5 ч | **6 GPU-ч на пару** |
| Численный pilot | 32 документа (16 коротких + 16 длинных), G1 + P | длинные scalar ~65 ток/с: 32K ≈ 8 мин/док/вариант | **4 GPU-ч** |
| Численный финальный срез | ≈ 560 документов (по ~80 на 7 обязательных ячеек; финальное N замораживается после pilot) | зависит от класса кандидата (см. ниже) | **по таймингам pilot** (решение владельца 2026-11-19: итоговый лимит уточняется реальными измерениями) |

Ключевые свойства стоимости:

- **Scalar `G1` читается один раз на замороженный корпус.** Эталонные логиты не зависят от кандидата, поэтому самый дорогой примитив (~16 мин на 64K-документ) оплачивается однократно и амортизируется между всеми последующими кандидатами.
- **Для `sparse`-кандидата scalar-чтение не нужно вовсе:** эталон — тот же бинарник со штатным FP16-путём (быстрый), кандидат — sparse (быстрый); teacher-forced логиты обеих сторон считаются матричными проходами. Численный срез для `T15` — самый дешёвый класс сравнений.
- Scalar-чтение полного корпуса нужно только для кандидатов класса «приближённый prefill/квантование» (`Q8_0` KV, `Q6_K`) — и то лишь для их P-стороны.

Ограничение дизайна: длинный срез **не превышает 30 % документов с длиной > 48K**, потому что G1 scalar-чтение 64K-документа — самый дорогой примитив (~16 мин). Полная матрица «все длины × все режимы» явно запрещена (как в черновике).

### 5.6. Судьба проверки `model-vision-serving-mtp` (35/36)

**Ничего не удаляется и не ослабляется автоматически.** Предлагается трёхшаговая процедура:

1. **Строгая проверка остаётся в наборе как есть** (`continued image cache differs from cold prefill`, код 1). Пока владелец не решил обратное, набор остаётся `35/36`, и это честный статус.
2. **Параллельно добавляется диагностическая проверка `vision-continuation-q1`** (в том же `vision_serving_test.cpp`, рядом с `DumpQwenVisionContinuationDiagnostic`): она фиксирует `common_max_logit_delta`, `common_max_KL_temperature1`, `first_divergence_step`, зазоры top1−top2 на шаге расхождения, факт ре-синхронизации — и **не влияет на PASS/FAIL** (только запись).
3. **Критерий квалификации после утверждения Q1 (решение владельца):** проверка `continued == cold` считается пройденной **по контракту Q1** тогда и только тогда, когда выполнено всё:
   - все оракулы уровня 1 точные (append/live-history/snapshot/chunk-инвариантность);
   - `common_max_KL_temperature1 ≤ κ = 0,010 nat` (наблюдено 0,001963 — запас ~5×);
   - `common_max_logit_delta ≤ 1,0` (верх документированного диапазона MoE-шума 0,09–0,82 с запасом ~20 %; наблюдено 0,513805);
   - расхождение argmax произошло на почти равной паре: зазор top1−top2 < 0,15 хотя бы у одной стороны (наблюдено 0,030/0,070);
   - тексты после точки расхождения совпадают при **выравнивании со сдвигом**: допускается offset-сдвиг или расстояние редактирования (edit distance) ≤ 2 токенов — сравнение **не по одинаковому индексу шага**, а по выровненным последовательностям; оба ответа содержательны и эквивалентны по смыслу (автопроверка по фиксированному эталону красного изображения);
   - `cold_trajectory_matches_serving = 1`.

   При выполнении — владелец отдельным решением признаёт `36/36` с формулировкой «пройдено по контракту Q1 с численными барьерами», и это **не** переписывание старого FAIL: исторический результат остаётся, а новый статус публикуется с датой и manifest. Если хоть один критерий нарушен — проверка продолжает считаться падающей.
