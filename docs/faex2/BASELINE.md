# Baseline FAEX2: сохранённые результаты 2026-11-09

Это обезличенная сводка уже выполненных измерений, **не новый прогон и не production-сертификация**. Полный сырой корпус и harness пока остаются в локальном эксплуатационном архиве владельца; публичная воспроизводимость ещё не завершена. Доступ к архиву — через локальную `.local/HANDOFF.md`, не через опубликованные личные материалы.

## Условия и происхождение

- FEVM FAEX2, Ryzen AI Max+ PRO 495, 128 ГБ RAM, gfx1151, ECO 100 Вт.
- Linux/CachyOS, HIP, TheRock ROCm 10.1.0; NPU выключен. Полный manifest compiler/dependencies/весов ещё предстоит собрать из исходных логов, не достраивать по памяти.
- Target `Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf`, встроенный MTP; экспериментальный draft `Qwen3.6-35B-A3B-DFlash2-Q8_0.gguf`; vision `mmproj-BF16.gguf` именно этой модели.
- Обычные прогоны: 4 слота × 131072; память отдельно 4 × 262144.
- Greedy — temperature 0. Sampling preset — temperature 1, top_k 20, top_p 0,95, min_p 0,05; это параметры прогонов, не универсальные defaults движка.
- Контроль: локальная vendor-база `6a107cf6` с необходимым build workaround; кандидат — последовательность пяти изменений, сейчас представленная кодом до `2c9c6b02`.
- Замеры делались до разовой замены email. При ней доказано равенство **каждого дерева файлов**, но новые бинарники не собирались. Результаты разных этапов нельзя выдавать за один общий замер конечного бинарника.

## Генерация на прозе, tok/s на поток

Этап перемера MTP/DFlash, до финального ускорения vision:

| Режим | 1 запрос, greedy / sampling | 2 запроса, greedy | 4 запроса, greedy / sampling |
|---|---|---|---|
| off | 64,6 / 63,7 | 50,6 | 36,7 / 35,9 |
| MTP 1 с патчами | 77,7 / 74,5 | 53,8 | 36,0 / 35,0 |
| MTP 2 с патчами | 76,3 / 72,7 | 50,0 | 35,9 / 34,9 |
| DFlash adaptive 7, исходный | 55,2 / 55,6 | 40,9 | 29,3 / 25,8 |
| DFlash adaptive 7, MoE-профиль | 60,7 / 59,2 | 45,3 | 30,6 / 29,7 |

Отдельный дополнительный прогон **двух запросов с sampling**: off 49,7; MTP1 53,1 (+6,8%); MTP2 48,5. С учётом этого прогона и критерия многопользовательской прозы выбран **MTP1**, а не MTP2. Числа нельзя смешивать в одно среднее без учёта этапов.

Для кода MTP1 greedy дал 88,8 tok/s, MTP2 — 101,3; DFlash может быть быстрее на коде, но это вторичный сценарий и не основание менять общий семейный пресет.

## Контекст, память, рассуждения

- MTP1, холодная история ~113K токенов — 76,6 с; повторный ход — 1,1 с. Не считать это SLA для любой истории.
- Память GPU при 4 × 262144: off 47,1 GiB; MTP1 без зрения 53,3 GiB; с проектором зрения 55,2 GiB. Это метрика GPU used, не вся память системы.
- Рассуждения, один запрос: 80–84 tok/s против ~63 без черновика. При четырёх — 38–41 против 39–40 на поток, то есть ускорение не сохраняется автоматически.
- `reasoning_effort: low` не сокращал длину стабильно. Серверный `--reasoning-budget 512`: содержательный ответ через 6,2–7,0 с для одного и 15,1–15,7 с при четырёх. Лимит общий для сервера, не per-agent.

## Зрение после ускорения

Чистый encoder, **лучшее из трёх тёплых прогонов**:

| Вариант | Синтетическое изображение 1170×2532 | 2048×2048 |
|---|---|---|
| Исходный FP32-score путь | 8,653 с | 18,558 с |
| hipBLAS с BF16 scores | 6,557 с | 14,554 с |
| Fused attention | 1,988 с | 3,557 с |

TTFT отдельного server-теста: 10,1 → 3,4 с и 20,3 → 5,4 с соответственно. Оценки llama.cpp в том же исследовании: ~6,0 / ~9,8 с TTFT; оценка encoder получена вычитанием «картинка − текст», поэтому методика не идентична прямому encoder timing.

12 реальных скриншотов: 12/12 верных по использованной проверке. Личные изображения и ответы не публикуются. Один начальный прогон после смены ядра был загрязнён старым кэшем и отброшен; после включения варианта attention в encoder identity проверка повторена.

Cosine эмбеддингов к исходному пути около 0,999; уже переход на BF16 scores даёт близкий порядок расхождения. **Это не доказательство качества на всех изображениях**, не битовое равенство и не CPU-reference для полного encoder.

## Что проверено и что ещё нет

Исторически прошли smoke/tools, 2/4 параллельных запроса, длинный контекст/повторный кэш, ограниченный vision-набор, policy-тесты и численные тесты vision. Детальная граница покрытия — [DESIGN.md](DESIGN.md).

Не завершены: сквозная статистическая квалификация sampled-MTP, переходы нагрузки и весь жизненный цикл кэшей, широкий русский/школьный/vision набор, мультиизображения, длительная работа 24/7, полная изоляция семейных сценариев, чистая воспроизводимая публикация harness/manifest и аппаратная проверка NPU. Dense-модели не входят в нашу квалификацию.

## Как использовать baseline

1. Не повторять все замеры только из-за появления документации или изменения email.
2. Для сравнения нового кода восстановить одинаковые веса, окружение, питание, sampler, форму нагрузки и историю кэша.
3. Новый прогон сохранять отдельно; учитывать ошибки и вариативность. Не объединять повторы одного SPEC без явного идентификатора прогона.
4. При смене общего пути расширять тесты по области риска. Успех CPU policy при model skip 77 не выдавать за GPU/model pass.
5. Сохранять source SHA и tree identity: git metadata и содержимое кода — разные вещи.
