# Проверяющий инструмент FAEX2: B0 и первый B1

**B0 реализован и проверен без модели: 24 новых CPU-теста и 7 shared checks. Затем первый реальный B1 выполнен 2026-11-10: 9 генераций + 4 discovery-запроса клиента PASS, сервер штатно остановлен. [Результат и границы качества](B1_RESULT.md).** Исходный профиль B1 сохранён. Расширение B2/B3/C описано ниже; готовность тестового инструмента не означает успешную приёмку модели.

## Устройство

[faex2.py](../../tests/functional/faex2.py) содержит две отдельные команды:

- `serve` — будущий процесс на FAEX2 в собственной tmux-сессии. Проверяет хеши бинарника/весов/переданных библиотек и точную версию, запускает один сервер на loopback, публикует `ready.json` после проверки API и реального loaded mode. При stop-request, ошибке или сроке завершает только свою группу процессов. Использует стандартную библиотеку Python; установки пакетов на FAEX2 нет.
- `check` — клиент на Mac через отдельный SSH tunnel. Сверяет живые `/health`, `/ready`, `/props`, `/v1/models` с записью запуска; проверяет ответы на фиксированные задачи. Успех не выдаётся только по HTTP 200 или коду завершения процесса.

`validate-config` проверяет только структуру manifest, не открывает веса и не запускает бинарник. Неизвестный SHA нельзя заменить заглушкой и объявить manifest готовым.

Повторно используются [metrics.py](../../tests/functional/metrics.py) для wire/usage/schema/таймингов и [discovery.py](../../tests/functional/discovery.py) для списка модели. Новый код добавляет только ограниченный транспорт и управление собственным процессом; общий SDK-runner и его матрица не меняются. Использовать `python`, без `-O`: у общих проверок есть assertions.

## Зафиксированный B1

Серверные параметры: `--speculative off`, `--think off`, `--sessions 1`, `--context 8192`, `--max-request-bytes 1048576`, cache-ram/cache-disk bytes 0, stall-timeout 120000 ms. Явно заданы temperature 1, top_k 20, top_p 0.95, min_p 0.05, presence/frequency penalty 0, repeat_penalty 1, repeat_last_n 64. Настройки проверяются через `/props`, поэтому профиль `qwen38` другой модели не подставляется. NPU OFF в закреплённом артефакте; очищенное окружение не передаёт GUFO_NPU_DIR, LD_PRELOAD или аппаратные overrides.

[Фикстуры](../../tests/functional/faex2_cases.jsonl) содержат только синтетические задачи:

| Случай | Проверка |
|---|---|
| Арифметика | 17×23 → ровно `391`, buffered и SSE |
| Русское извлечение | Название птицы → ровно `сова` |
| JSON Schema | Точные answer/bird и отсутствие лишних полей, buffered и SSE |
| Два независимых диалога | Разные точные маркеры, без смешивания |
| Инструмент | Ровно `lookup` с заданными аргументами; фиксированный локальный result; точный SSE-ответ продолжения |

Ни одна функция по ответу модели не исполняется. Имя/JSON аргументов проверяются, затем в историю подставляется уже известный литерал. Это проверка протокола tool call, не поиск в интернете.

Дополнительно обязательны корректные finish_reason/usage/счётчики drafts, формат HTTP, окончание SSE, непустой ответ и отсутствие reasoning при off. Тайминги записываются для каждого запроса; B1 отчёт содержит `RECORDED_NOT_COMPARED`, а не заявление об отсутствии регрессий.

## Ограничения времени и сохранность

- Только новый output. Существующий каталог или symlink отвергается; чужие файлы не перезаписываются.
- Занятый серверный порт — отказ до исполнения бинарника; резервирование сохраняется до запуска. Перед READY принадлежность listener своему PID проверяется через `/proc` на Linux, через системный lsof в CPU-тестах на Mac. Старые wrappers, pkill/killall и системные настройки не используются.
- Готовность до 240 с, отдельный запрос до 120 с, время жизни сервера/клиента максимум 900 с. Медленные заголовки/частичные ответы не обходят deadline. На остановку своего процесса допускается дополнительное короткое время (SIGINT, затем SIGKILL).
- Полные request JSON и response bytes/SSE пишутся до валидации. При timeout/failure сохраняются частичный ответ, предыдущие результаты, server log, config и cache; очистки нет.
- `ready.json` не является окончательным успехом сервера: после проверки клиента обязательно запросить остановку и проверить итоговый `server-result.json`. Обрыв SSH не требует нового запуска: читать ту же tmux-сессию/output; собственный deadline ограничивает оставшуюся работу.
- Код 77, неверная версия/режим, отсутствующая метрика, обрезанный ответ или пропущенная проверка не превращаются в PASS.

## Проверки без модели

На Mac используется отдельно разрешённое окружение `.local/venv-faex2-b0` с Python 3.12 и [клиентской зависимостью](../../tests/functional/faex2-requirements.txt). Оно исключено из Git. Существующий общий requirements.txt остаётся для полного SDK-набора и не устанавливается этим этапом.

```bash
.local/venv-faex2-b0/bin/python -m unittest discover -s tests/functional -p test_faex2.py
```

[Тесты](../../tests/functional/test_faex2.py) используют собственный [подставной HTTP-процесс](../../tests/functional/fixtures/faex2_fake_server.py), фиктивный маленький файл вместо весов и loopback Mac. Настоящий gufo не вызывается. Проверяются положительный B1-сценарий и отказные случаи, сохранность результатов, завершение только своего процесса, deadlines и неизменность постороннего процесса. Серверная часть дополнительно должна импортироваться без site-packages; клиенту нужен jsonschema.

Независимое ревью выявило продление внешнего deadline вложенным таймером, подмену полного B1 через `--cases`, нормализацию повреждённого tool type и отсутствие доказательства владения listener. Все четыре случая воспроизведены тестами и исправлены. Linux-парсер проверен на фиксированном `/proc/net/tcp`; реального Linux/model-прогона в B0 нет. В B1 используется фиксированный набор, опции `--cases` нет.

## Перед первым реальным запуском

Первый B1 выполнен с отдельного согласия; полный хеш нужных весов снят и проверен worker перед загрузкой. Точный пакет/результаты находятся в эксплуатационном проекте из `.local/HANDOFF.md`. Следующий запуск получает новый каталог и отдельное согласие; исторические команды не повторять автоматически. После B1 уточнено: `--cache-ram-bytes 0` выбирает автоматическую ёмкость (32 GiB в этом прогоне), не отключает RAM cache. Snapshot bytes ненулевые; disk cache выключен, cached tokens 0.

## Расширение B2/B3/C

`faex2.py serve` принимает ограниченные profiles по [плану приёмки](ACCEPTANCE_PLAN.md): явные MTP1/off, slots/context, projector+SHA, thinking/budget512, RAM/disk/request limits и отдельный существующий `run_root`. Output и cache — разные подкаталоги этого корня; cache сохраняется при остановке и повторном запуске. На Linux каждые 2 секунды записываются RSS/GTT/MemAvailable/температуры; недоступная обязательная метрика, отказ записи или нарушение лимита останавливает собственный процесс. READY требует mode/draft/thinking и фактическую загрузку projector (`vision_prepared`, resident_bytes>0); работа drafts подтверждается позже по usage.

`faex2_transport.py request --base-url http://127.0.0.1:PORT --request FILE --output NEWDIR --timeout SECONDS` выполняет ровно один HTTP-запрос с hard deadline≤600с и сохраняет полный request/raw/parts/result. Вход содержит `method`, `path`, `body`. Внешние адреса и неподдерживаемые endpoints запрещены. Для параллельности `faex2_acceptance.Runner` запускает отдельные процессы; результаты и времена каждого запроса сохраняются раздельно. Ожидаемая HTTP-ошибка и намеренная отмена проверяются отдельными критериями.

`faex2_acceptance.py b2 --server-record FILE --base-url http://127.0.0.1:PORT --output NEWDIR` выполняет discovery, девять базовых генераций B1, длинный русский C1 с настоящими proposed/accepted drafts, девять vision-проверок (включая ожидаемую ошибку) и 12 русских/школьных заданий. Для изображений проверяются содержание и свежий полный prefill. PNG и текст GUFO 742 строятся независимо от модели; JPEG/WebP — существующие фиксированные fixtures. Рубрика и goldens закреплены до запуска в `faex2_quality.jsonl`; `NEEDS_REVIEW` остаётся до прочтения всех объяснений и отдельной ручной оценки.

Движок, его defaults и исходный SDK-runner не изменены. Модельные результаты и личные команды/пути сохраняются в эксплуатационном проекте. Синтетическое OCR не квалифицирует произвольные фотографии или рукописные задания.

## Подготовленные клиенты B3 и C

`faex2_family.run_family(runner, phase="initial"|"restart", state_path=...)` проверяет переходы 1→2→4→1, калибрует длинную историю по фактическим usage, проверяет три ключа, продолжение, редактирование, cache, отмену и Responses budget512. State и журнал создаются без перезаписи. Фактическую ширину, опубликованный disk checkpoint и допустимость ненулевого малого prefill исполнитель подтверждает по serverlog; успешные клиентские проверки сами по себе не закрывают B3.

Перед измеряемым edit выполняется отдельный `branch-warmup` с третьим ключом. Он создаёт ранее отсутствующую общую recurrent checkpoint-границу; его полный prefill допустим и сохраняется отдельной фазой, включая сравнение C. Целевой edit с исходным новым ключом по-прежнему требует cached≥depth−256/prefill≤256 и не запрашивается заранее. [Причина и исходный FAIL](B3_RESULT.md).

`faex2_stability.run_control(runner, records, groups=None)` сохраняет одинаковые входы и полные cache histories. `compare_reports` проверяет условия и каждую фазу отдельно при одновременно >5% и >3мс, без усреднения. Флаг означает необходимость расследования. `run_soak` требует 600с прогрева и 1800с измерения, сохраняет границы фаз и фиксированные C1/C2/C4 истории. Квалификация памяти и ядра выполняется отдельно по монитору с интервалом 2с.

После независимого ревью каждый control (полный и выборочный) начинается отдельным sampled C1-запросом с 40 квадратами и точным JSON golden. Он требует proposed>0 и accepted>0, входит в историю и сравнение времени. `compare_reports` повторно проверяет этот gate; старый control v1 без доказательства не принимается. Разные положительные счётчики MTP допустимы; C2/C4 могут отключать drafts по внутренней политике. 19 CPU-тестов C прошли. Это готовность клиента, не модельный PASS. Исправление Q8 уже проверено; реальные B3/C ещё не выполнены, управление процессами B3 проверяется отдельно.

## Зрительные пробы в приёмочном прогоне (2026-11-11)

`faex2_acceptance.py b2` после прежних визуальных случаев выполняет все пробы [faex2_vision_probes.py](../../tests/functional/faex2_vision_probes.py); исходная фикстура `GUFO 742` — первая из них. Проба с известным ограничением при неверном ответе получает статус `KNOWN_LIMIT_FAIL`, прогон продолжается, а итог отчёта становится `KNOWN_FAILURES` — не PASS. Ограничение покрывает только содержание ответа: сбой транспорта, HTTP или незавершённый ответ остаются обычным FAIL. Если такая проба неожиданно прошла, она попадает в `unexpected_probe_passes`.

Клиент можно запускать на самой машине, без SSH-туннеля. Там нет `jsonschema`; допустима только явная заглушка с обязательным повторным разбором сохранённых ответов штатным `parse_response` на машине разработчика. Без повторного разбора прогон не считается пройденным.

## Исправления сравнения задержек 2026-11-10

`wall_ms` заканчивается на последнем байте тела ответа; разбор и проверки клиента записываются отдельно в `client_post_wire_ms` и `client_total_ms`. Отчёты, снятые раньше, содержат прежний `wall_ms` и напрямую с новыми не сравнимы.

Запросы параллельной группы отправляются отдельными процессами, поэтому порядок их допуска сервером не определён. Если место запроса (`resident_requests_at_admission`) различается между прогонами, `compare_reports` помечает его TTFT и клиентский TTFA как `UNMATCHED_ADMISSION` и добавляет строки `…#admission-N`, где сравниваются запросы с одинаковым местом. Полное время `wall_ms` от места почти не зависит и всегда сравнивается по имени. Пороги 5 % и 3 мс прежние. Без однозначных мест с обеих сторон действует прежнее сравнение по имени. [Причина](INVESTIGATION_RESULT.md).

## Старый контроль с неизвестной встроенной ревизией

Сохранённый эксплуатационный бинарник сообщает `gufo version development (unknown)`.
Только для стадии C разрешено явно указать `expected_version` с этой точной строкой
и завершающим `\n`. Это не автоматический fallback: без поля требуется полный
`source_sha`, как прежде. Та же версия проверяется в `/props`; произвольные строки
и такое исключение для B1/B2/B3 отвергаются.

Полный SHA-256 бинарника, весов, projector и библиотек проверяется до запуска и
не ослабляется. `source_sha` старого контроля относится к проверенному source-клону;
его нельзя выдавать за встроенную или заново доказанную ревизию сборки. Контроль
сравнивает закреплённый прежний эксплуатационный артефакт с кандидатом.
39 CPU-тестов, включая запуск fake legacy-server и отказ после изменения его байтов,
прошли; новые отрицательные проверки сначала воспроизвели неподдерживаемый контракт.
