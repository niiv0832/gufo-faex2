## B1–B3. Функциональные этапы — отдельное модельное разрешение

Сначала кандидат. Для каждого этапа новые output/cache, проверка готовности до 240 с и каждого короткого запроса до 120 с. Таймаут — наблюдаемый FAIL, не основание молча увеличить предел. Общий лимит B1 — 15 мин, B2 — 30 мин; длинные B3 случаи планировать отдельно по сохранённым данным. Если readiness/лог или memory показывают проблему, остановить только собственный процесс и сохранить материалы.

| Этап | Конфигурация | Обязательное покрытие и ожидаемый результат |
|---|---|---|
| B1: минимальный API | off, 1 слот × 8192, без mmproj и дискового кэша | `/health`, `/ready`, `/v1/models`; арифметика 17×23=391, короткая русская инструкция, buffered и SSE; JSON/schema; один фиктивный tool call и продолжение с tool result. Нужны корректные HTTP/usage/finish_reason, непустой содержательный ответ, валидные аргументы, завершённый поток |
| B2: выбранный режим | MTP 1 (`--mtp-model embedded --draft-tokens 1`), 1 слот × 8192, соответствующий mmproj BF16 | Повтор выбранных B1 контрактов; фактически loaded MTP и ненулевые предложенные/принятые drafts на достаточно длинном одиночном ответе (C1); синтетические красное PNG/JPEG/WebP, текстовая картинка с заранее известной строкой, два изображения, повреждённый base64. Форматы/ошибки брать из [image_inputs](../../tests/functional/image_inputs.py), не из семейных фото |
| B3: семейный профиль | MTP 1 + vision, 4 слота × 131072; off как отдельный контроль затронутых случаев | Переходы 1→2→4→1, разные session markers; reasoning off/on и серверный бюджет 512; короткая/длинная история, повтор/редактирование префикса, отмена→повтор, disk restart только своего сервера. Содержимое/изоляция/ожидаемая работа prefill/cache обязательны; длинный контекст подтверждать реальным usage, не пересчётом символов |

В B3 MoE MTP-gate зависит от размера пакета предложений: отсутствие drafts при большой группе не объявлять поломкой автоматически; обязательно наблюдать возврат draft-работы на следующем C1. Нельзя считать сам флаг `--speculative mtp` доказательством исполнения MTP.

Фикстуры B1/B2: минимум одна строгая задача на арифметику, извлечение, JSON и tool schema; goldens фиксируются до запуска. Для B3 минимум четыре непересекающихся session markers, отдельный длинный текст со вставленными ключами, проверка наличия/отсутствия ожидаемых ключей. Пустой/обрезанный ответ, неверный инструмент или утечка между сессиями — FAIL, даже при высокой скорости. Если рассуждения съели весь бюджет и содержательного ответа нет, это не успешный ответ.

Покрытие SDK-модулей выбирать явно: discovery, stops/conversation/structured, tools/tool-streaming, image-inputs; затем batch, long-context, cache и reasoning-budget после проверки их применимости. Не запускать `--suite all`, Flash-Next-specific recovery, полные sweeps или агентские CLI автоматически. При изменении continuation обязательны long-context/cache; реальный агентский цикл требует отдельного [pi_agent](../../tests/functional/pi_agent.py) replay, если такой сценарий входит в утверждённую приёмку.

## C. Сравнение, численное качество и длительная работа

- [ ] Для каждого запроса/фазы сохранить startup, prefill, decode, TTFT, TTFA, wall time, usage/cache/draft counters, ошибки, память и историю кэша. Пороги сравнения — одновременно более 5% и более 3 мс; не усреднять регрессию между запросами. Шум остаётся INCONCLUSIVE.
- [ ] Старый кандидат запускать только для затронутых timing-controls при совпадении весов, toolchain, harness, sampler, питания и cache history. Старые цифры BASELINE не являются автоматическим baseline новой сборки. При несовпадении manifest сравнение только наблюдательное. Не повторять полный correctness-набор на контроле.
- [ ] Подтверждённую регрессию расследовать повтором только затронутой истории, чередуя контроль/кандидат. Не расширять допуски и не выбирать лучший повтор; сохранять все результаты.
- [ ] Для квалификации MTP/vision сохранить независимые policy/numerical проверки из [DESIGN §5](DESIGN.md#5-тесты-и-доказательства). Их отдельная сборка/запуск требуют разрешения. Skip 77 не PASS; одинаковый seed/похожий текст не доказывают распределительную эквивалентность sampled-MTP.
- [ ] Сохранить стандартный speed benchmark выбранной 35B-модели с теми же входами и manifest; конкретную ограниченную команду определить до отдельного разрешения. Функциональные ответы и отдельные красивые цифры скорости его не заменяют.
- [ ] Разобрать релевантные предупреждения сборки до функциональной приёмки, особенно alignment и dangling-reference. Сейчас они не устранены и не объявлены безопасными. Чтение исходников само по себе не заменяет численную проверку.
- [ ] После B1–B3 определить и согласовать отдельный ограниченный soak, критерии роста памяти, отмены/восстановления и SLA; не объявлять 24/7-ready по короткому smoke.

## Доказательства и решение

Каждый отчёт: точный source/binary/harness SHA, веса и их SHA-256, projector, compiler/packages, env без секретов, полная команда, power profile, sessions/context/sampler, fixture hashes, request/response/SSE, логи, exit-коды, тайминги каждого запроса и его предыстория. Личные пути/изображения/ответы остаются непубличными.

Статусы: PASS, FAIL, SKIP/NOT RUN, INCONCLUSIVE отдельно по проверкам. Отсутствующие веса, неустановленный клиент или неподходящий профиль — остановка подготовки, а не успех. CLI PASS разрешает только предложить B1, B1/B2 PASS — B3, полный согласованный набор — отдельное решение о смене default. Автоматического deploy, удаления старого бинарника, публикации или включения NPU нет.
