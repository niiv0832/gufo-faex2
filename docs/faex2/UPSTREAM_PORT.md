## 2. Исходное положение

- **32 коммита upstream уже есть в ветке.** Vendor-линия выборочно перенесла их (примерно до #676), в том числе `23d970d0`, `a802cc77`, `f948ddd3`, `9a9717c1`, `0604e9eb`, `95ba1eae`, `d1830de7`. Повторно не переносить.
- **В upstream нет 35B-A3B.** MoE-путь (`moe_ffn.cpp`, `moe_prefill*.cpp`, `gemm_route.hpp`, `mtp_policy.hpp`) существует только у нас и в vendor. Любой перенос в эти места — ручной.
- **Кэш продолжений у нас другой.** Qwen обслуживается старым `ContinuationCache` (`src/cli/serve/continuation_cache.cpp`). Библиотека `src/cache` (component cache) подключена только к Flash-Next. Около 20 фиксов `src/cache` из upstream на 35B сейчас не действуют.
- **Длинный prefill уже не блокирует соседей.** При активном декодере планировщик (`StepPrefill` в `text_generation_scheduler.cpp`) режет prefill на порции `--prefill-chunk`, по умолчанию 512 токенов. Плата — скорость самого prefill.
- **Стенд собран HIP Clang 24.0.0** (TheRock 10.1.0, см. [Q8_MEMORY_RESULT.md](Q8_MEMORY_RESULT.md)). Upstream после нашей базы отдельно чинил ядра Qwen именно под LLVM 24.
- **Одну ошибку upstream мы уже нашли сами.** `2f10b15d` (размер scratch Q8_0 с учётом sum sidecar) — то же исправление, что наш `49f3c8cd`. Переносить не нужно; вывод на будущее — просматривать фиксы upstream в общих ядрах до собственного расследования.

## 3. Пакеты переноса

### Пакет A — ядра K-квантов и LLVM 24 (скорость decode/prefill, корректность)

**Статус 2026-11-11:** перенесён (`369b3c94`, `0ea25929`, `e45434bd`, `8d26f54c`, `92239590`, правка теста `17748812`). Кандидат A+B прошёл приёмку: ответы равны рабочему бинарнику, prefill коротких дозагрузок длинной истории быстрее на 9–22 %, холодный prefill и decode без изменений; `369b3c94` чинит падающий на нашем компиляторе `qwen_ssm_ops_test`. Рабочим не назначен — см. [журнал](CHANGELOG.md). Ниже — исходная оценка.

| Upstream | Суть | Наши файлы | Накладываемость |
|---|---|---|---|
| `c0e0be58`, только часть Qwen | LLVM 24: `attention_wmma` занимает 241 VGPR и теряет заполнение волн; в `ssm_row_split` плавает округление FP16 | `hip/kernels/attention_wmma.hip`, `ssm_row_split.hip` | `attention_wmma` — конфликт (у нас vendor-вариант «16 голов поверх 2»), `ssm_row_split` — чисто |
| `56ed8f4d` | IQ4 small-batch: шаг по токенам, чтобы LLVM 24 не делал spill регистров | `hip/kernels/small_batch_wave64.hip` | чисто |
| `1c75887b` | специализированное скалярное произведение K-квантов, GEMV «строка на warp» | `hip/quant_ops.hpp`, `hip/kernels/gemv_quant.hip` | чисто |
| `1fc829ea` | prefill GEMM на 9–15 строк одним маскированным 16-строчным проходом | `hip/kernels/prefill_quant_gemm.hip`, `small_batch_*`, `hip/ops/gemm.hpp` | чисто |

Почему это относится к 35B:

- decode MoE вызывает `LaunchGEMV` для роутера, общего эксперта и выходной проекции (`moe_ffn.cpp`, `decode_step.cpp`);
- пакетный decode на 2–8 строк идёт через `LaunchBatchedQuantGEMMFp32` (`batched_decode.cpp`) — это и 4 слота, и проверка MTP;
- веса UD-Q4_K_XL — смесь Q4_K, IQ4, Q5_K, Q6_K, все исполняются упакованными (`gemm_route.hpp`).

Не установлено: затрагивают ли эти ядра grouped-expert prefill (`moe_prefill_ffn.cpp`) и какова величина выигрыша. Правка `ssm_row_split` меняет порядок округления — возможен сдвиг численного результата; нужен контроль по CPU-reference.

### Пакет C — память и загрузка весов (устойчивость длительной работы)

- `bff0eec6` — снимки дискового кэша пишутся мимо page cache. Правит наш `continuation_disk_store.cpp` чисто. На 128 ГБ общей памяти page cache конкурирует с GPU.
- Цепочка «веса в памяти устройства»: `5131f348` → `2765d65e` → `abbc5cb8`. Причина по описанию upstream: зарегистрированная анонимная копия весов лежит в LRU ядра; при компакции памяти драйвер выгружает и восстанавливает GPU-отображение, и ядра замирают на секунды. Наш `model_loader.cpp` использует именно этот путь (`MapRegisteredRegion`, `hipHostRegister`).
  - Отсутствующие зависимости: `src/core/hip/heap_placement.hpp` (из `248d902e`) и `src/core/platform/pages*` (`ddc31dc7`, `5c8bb390`).
  - Перенос по смыслу в наш загрузчик; из `platform/pages` нужна только POSIX-часть.
  - Особенность 35B: Q6_K-тензоры экспертов перекодируются в Q8_0 при загрузке и не являются файловыми регионами — для них логика отдельная.
  - Наблюдались ли такие замирания на FAEX2, не проверялось. До переноса — сначала поиск признака в сохранённых прогонах C.

### Пакет D — prefill рядом с декодерами (только после замера)

Идея `1e74ffa4` + `90b9745f`: сохранять эффективный проход 4096 строк и уступать декодерам между группами слоёв, а не резать prompt по 512 токенов.

- Сторона движка мала: крючок в `QwenGpuExecutor::PrefillLayerCheckpoint` (есть у нас, вызывается из цикла слоёв в `prefill_chunk.cpp`) и новый `SetPrefillYield`.
- Сторона планировщика в upstream опирается на `src/sched` и ext-контракты, которых у нас нет. Нужен собственный минимальный вариант в `StepPrefill`: при активном декодере — полный проход с колбэком «один раунд decode».
- Риски именно MoE: владение рабочими буферами MoE-prefill (уже исправлялось в `f3e8fc32`, `67007f07`, `d891354f` — перепроверить для decode внутри уступки), lock-step пары порций с собственными уступками (`ForwardPromptChunkPair`, `GUFO_QWEN_LOCKSTEP_YIELDS`), захват признаков для MTP во время prefill.
- **Ворота:** измерить prefill 35B порциями 512 и 4096 при одном активном декодере. При малой разнице пакет не делать.

## 4. Отложено и не переносится

Отложено до появления измеренной причины:

- **Переезд Qwen на component cache** — `da5d5a2b` и следующие фиксы (`fe2694bc`, `31c3b3a0`, `0d12f7b7`, `3016d652` и др.). Один `da5d5a2b` меняет `inference_backend.cpp` примерно на 1000 строк, адаптера для MoE нет. Возвращаться, если нагрузка четырёх агентов покажет проблемы старого кэша.
- Зрение: `d8138a01` (`detail: low`), `ce617610` (sidecar при повторном запуске). Конфликтуют с нашим fused-attention и отсутствующими у нас файлами.
- `fe9498d1` (GCC 16, `<format>`) — пересекается с нашим `5409fdd9`; сверить при следующей пересборке.

Не переносить:

- extension-инфраструктуру (`6b6a6b04` и серия `feat(ext)`);
- Flash-Next, DeepSeek, TTS/ASR, embeddings, генерацию изображений, Windows, CI/release;
- ускорения DFlash2 (режим не выбран для семейного пресета);
- `c2292921` — добавляет Rust в сборку ради декодирования PNG;
- `1b8ad798` — отменён самим upstream (`24796139`);
- `9bd24d26` — убирает проверку API-ключа.

## 5. Порядок и правила

1. Порядок: **B → A → C → замер → D → E.** B проверяется без GPU; A даёт измеримую скорость; C и D требуют стенда и длинных прогонов.
2. Каждый пакет — серия малых коммитов в `faex2`. Чистые патчи — `git cherry-pick -x` либо наложение с пересчётом путей; остальные — ручной перенос с SHA upstream в сообщении. Без rebase, без merge upstream, без push без согласия.
3. Каждый пакет начинается отдельным поручением владельца. Сборка и запуск на FAEX2 — только после отдельного согласия, кандидат в отдельном каталоге, рабочий и резервный бинарники сохраняются.
4. Перед началом пакета выполнить `git fetch upstream` (с согласия) и проверить, не появились ли исправления переносимых коммитов.
