# NPU (XDNA2) в FAEX2: карта статуса, возможностей и условий включения

Подготовлено 2026-11-09 как read-only анализ агента; машина не трогалась,
код не менялся. Цель — зафиксировать, **зачем NPU в ветке, почему он
выключен и при каких условиях его стоит пересматривать**, чтобы будущие
сессии не пересматривали вопрос заново. Числа — из унаследованных
документов и vendor-линии, не с FAEX2.

## 1. Главный вывод

1. **Стек NPU уже присутствует в ветке** — он унаследован от vendor-линии
   (`mikealanni/gufo`, `fork-enhancements`) через базу `6a107cf6`:
   мерж `9982eaf6` и его документация `3642b212` — предки базы.
   **Переносить из vendor нечего**; проверено: `git merge-base --is-ancestor`.
2. Он **выключен дважды**: опция сборки `GUFO_ENABLE_NPU` (по умолчанию
   `OFF`) и переменная окружения `GUFO_NPU_DIR` (не задана → GPU-only).
3. Причина выключения — не gufo, а **платформенный дефект AMD Strix Halo
   Data Fabric**: одновременная работа iGPU и NPU может приводить к
   machine check и жёсткому зависанию машины. Сводка —
   [NPU_FREEZE.md](../NPU_FREEZE.md).
4. Даже когда дефект уйдёт, NPU для Qwen3.6-35B-A3B даёт **только prefill**:
   +1,1% при промптах 2K, +8,7% при 4K, +9,5% при 8K (замеры vendor).
   **Decode не ускоряется** — он остаётся на GPU и упирается в общую
   LPDDR5X-память, которую NPU не добавляет.
5. Опасность «GPU+NPU одновременно» — **платформенная**, она касается
   любого ПО, включая FastFlowLM, а не только gufo.

## 2. Происхождение и инвентарь

Точка расхождения веток: `git merge-base faex2 vendor/fork-enhancements` =
`6a107cf6` (база форка). Значит, весь NPU-стек vendor'а до этой точки уже
в нашей истории. Ключевые коммиты стека, присутствующие в ветке:

| Коммит | Содержание |

| `1c00f953` | 35B-A3B: ведущие колонки `qkv`, `gate`, `ssm_out` линейных слоёв на NPU |
| `35dd096c` | 35B-A3B: ведущие колонки `attn_q`/`attn_output` full-attention слоёв на NPU |

| `736a9f4c` | Артефакты ядра: [tools/npu](../../tools/npu) — `.xclbin`, instruction streams, исходник `mm_bfp_mixed.cc` |

сборка) **не пересекаются по файлам** с NPU-стеком — проверено сравнением
списков файлов. Но сочетание NPU prefill с нашим sampled-MTP **не
тестировалось** ни vendor'ом, ни на FAEX2.

## 3. Измеренный эффект для 35B-A3B (vendor, Ryzen AI MAX+ 395)

UD-Q4_K_XL, fabric clock held, NPU в performance mode
([BENCHMARKS](../../docs/models/qwen3.6-35b-a3b/BENCHMARKS.md)):

| Prefill, tok/s | GPU only | GPU + NPU |
|---|---|---|
| `-p 2048` | 3 034 | 3 066 (+1,1%) |
| `-p 4096` | 3 013 | 3 276 (+8,7%) |
| `-p 8192` | 2 862 | 3 134 (+9,5%) |

Decode: plain 60,6 tok/s; MTP/DFlash2/auto — спекуляция на GPU, NPU в
декоде не участвует. Качество NPU prefill: изменение perplexity < 0,03%
против llama.cpp; KL 0,002–0,003 на routing near-ties.

Для семейного сценария это означает: ускорение загрузки длинных
контекстов и больших скриншотов на ~9%, скорость ответа — без изменений.

## 4. Почему выключено: дефект платформы

[NPU_FREEZE.md](../NPU_FREEZE.md) (2026-10-10) — read-only расследование.
Цепочка: runtime-PM suspend NPU → resume под полной GPU-нагрузкой → два
мастера одновременно бьют в Data Fabric во время перехода питания →
deferred machine check (bank MC28, syndrome `0x5b000000`) → sync flood →
**жёсткое зависание хоста, требуется power cycle**.

Внешние подтверждения (октябрь 2026):

- [ROCm/TheRock#8709](https://github.com/ROCm/TheRock/issues/8709) — инженер
  AMD воспроизвёл; AGESA 1.0.0.2b помогла на их стенде, но на Linux-хостах
  на 1.0.0.2b зависания сохраняются (SMU 100.7.0); FCLK-hold тоже не сработал.
- [amd/xdna-driver#1605](https://github.com/amd/xdna-driver/issues/1605) —
  то же, хуже: «data fabric deferred-error storm + MC28 + hard system hang»,
  воспроизведено на Ubuntu и mainline; «уменьшение нагрузки не помогает».
- [amd/IRON#103](https://github.com/amd/IRON/issues/103) — отказ
  `aie2_map_host_buf` на этом поколении прошивки (наш путь hipHostMalloc →
  XRT userptr).

Единственное проверенное в поле смягчение — **строгая сериализация**
(никогда не держать GPU и NPU в полёте одновременно), что обесценивает
сам смысл оффлоада-с перекрытием: выигрыш prefill'а при сериализации
исчезает, остаётся только последовательная смена устройств. Коммит
`59e57faf` прямо фиксирует: FCLK hold и AGESA 1.0.0.2b — **не
гарантированные** фиксы. Поэтому вердикт freeze-документа: держать
`GUFO_ENABLE_NPU` выключенным.

Замечание о конфликте документов: README vendor-линии и [NPU.md](../NPU.md)
описывают fabric-clock hold как обязательное требование запуска;
NPU_FREEZE.md объясняет, почему этого недостаточно. Freeze-документ новее
по сути решения и учитывает внешние данные.

## 5. Что появилось в vendor после нашей базы

Полный список NPU-коммитов `6a107cf6..vendor/fork-enhancements` — восемь,
и почти все про другое:

- `649824af` — **безопасность**: отбрасывать prefill с non-finite logits,
  отключать NPU после первого случая. Файлы — dense-путь flash-next
  (`npu_gemm.*`), для 35B напрямую не применяется, но паттерн
  «автоотключение при аномалии» стоит повторить при любом ретесте.
- Серия `72ecc927`…`de97448f` — «jev judge»: резидентная MiniCPM5-1B на NPU
  как компаньон-судья для агентских сессий. Это реализация единственного
  выгодного сценария «NPU исполняет постороннюю нагрузку» — но и он
  требует одновременной GPU+NPU работы, то есть упирается в тот же
  платформенный дефект.
- Дифф [NPU.md](../NPU.md) — 4 строки к тому же фиксy.

Развитие NPU для других моделей (glm53, flint, two-bank flash-next) — не
наш путь. Если когда-нибудь понадобится точечный перенос — только
cherry-pick с переписыванием метаданных на noreply; merge старой серверной
линии запрещён правилами форка (AGENTS, п. 6).

## 6. FastFlowLM, llama.cpp и другие движки

**FastFlowLM** ([ROCm/FastFlowLM](https://github.com/ROCm/FastFlowLM)):
теперь часть AMD/ROCm, с 03/2026 есть Linux; MIT на CLI/оркестрацию,
но **NPU-ядра закрыты** (binary license) — встроить их в gufo нельзя,
можно только использовать как отдельный продукт. Это NPU-only рантайм
(вся модель на NPU), поэтому decode 35B на нём будет заведомо медленнее
GPU-пути gufo. Реальная ниша — **второй сервер** для компаньон-нагрузок
([Whisper](https://fastflowlm.com/docs/models/whisper/),
[EmbeddingGemma](https://fastflowlm.com/docs/models/embeddinggemma/))
через OpenAI-совместимый API без интеграционного кода. По измерениям
апстрима компаньон на GPU отнимает у основной модели −34%, на NPU — −18%,
то есть перенос даёт основной LLM +23% во время работы ASR/эмбеддингов.
**Но**: это тот же одновременный GPU+NPU на том же Data Fabric — до фикса
прошивки применимы те же оговорки, что и для gufo.

**llama.cpp**: официального NPU-бэкенда нет
([feature request XDNA](https://github.com/ggml-org/llama.cpp/issues/21725)
открыт). Существует
[экспериментальный форк с ggml-xdna бэкендом](https://github.com/BrandedTamarasu-glitch/OllamaAMDNPU):
его собственный итог — 2,93 GOPS из 480 теоретических (0,6% утилизации
AIE), автор рекомендует для LLaMA 8B «использовать Vulkan исключительно».
Это независимое подтверждение потолка XDNA2 для той же платформы.
Переиспользовать для gufo нечего.

## 7. Дерево решений

- **Сейчас**: NPU остаётся выключенным — и по сборке, и в рантайме. Это
  соответствует этапу 8 CONTEXT («NPU и внешние PR — после GPU-базы»)
  и правилу «неизвестное качество не выдавать за lossless».
- **Триггеры пересмотра**: подтверждённое на Linux исправление в
  TheRock#8709 / xdna-driver#1605 (AGESA ≥ 1.0.0.2b с SMU 100.9.0,
  подтверждённое несколькими Linux-хостами), либо проверенный фикс в
  BIOS/прошивке FAEX2 от владельца.
- **Чек-лист безопасного ретеста** (из NPU_FREEZE.md, обязательный):
  сериализация GPU/NPU без перекрытия; без keepalive-потока;
  `GUFO_NPU_ISOLATE=0`; конечные таймауты на каждом `run.wait()`;
  мониторинг `journalctl -kf | grep -i "hardware error"` и
  `dmesg | grep "Previous system reset reason"` — подпись sync-flood
  `[0x08000800]`; длительный чистый soak на целевом хосте до продакшена.
- **Если ретест на 35B**: по методике [BASELINE.md](BASELINE.md)
  (интерливинг кандидатов, пороги 5%/3 мс, без усреднения); отдельно
  проверить сочетание NPU prefill с собственным sampled-MTP форка и
  качественные пороги vendor (KL 0,002–0,003, ppl < 0,03%); отдельная
  candidate-сборка, рабочий бинарник не трогать; ожидаемый максимум —
  ~+9% prefill на 8K-промптах, decode без изменений.
- **Параллельный вариант для компаньонов** (ASR/эмбеддинги через FLM) —
  тоже только после подтверждённого фикса платформы, см. выше.

## 8. Исправление прежних выводов этой сессии

В ходе этого разговора агент дважды сделал неверный промежуточный вывод:
сначала — что «апстрим удалил NPU-стек и переносить было бы нечего»
(верно только для `gufo-org/gufo`), затем — что перенос из vendor был бы
большим проектом. На самом деле стек уже в базе ветки, и никакой перенос
не требуется. Этот раздел оставлен, чтобы карта не расходилась с более
ранними ответами сессии.
