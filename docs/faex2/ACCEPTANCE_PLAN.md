# Завершение B2, B3, C и перевод рабочего запуска

> Для исполнителя: использовать superpowers:executing-plans, TDD для изменяемого harness и независимое итоговое ревью. Пользователь явно поручил самостоятельное выполнение всего этого плана, включая необходимые модельные запуски и переключение эксплуатации; push запрещён. Повторное согласование уже разрешённых этапов не требуется.

**Цель:** квалифицировать новый кандидат на выбранном семейном профиле и перевести существующий рабочий способ запуска на новый клон `faex2`, сохранив проверенный откат.

**Архитектура:** расширить ограниченный stdlib-worker B1 параметрами B2/B3/C; HTTP-проверки выполняются с Mac отдельными ограниченными процессами, что даёт настоящую параллельность без signal timers в потоках. Общие metrics/discovery/image fixtures переиспользуются. Личные manifests, SSH-команды, артефакты, эксплуатационные скрипты и доказательства переключения остаются в проекте машины.

**Стек:** существующие Python 3, jsonschema в разрешённом venv, Git, SSH, tmux, текущая сборка HIP gfx1151/NPU OFF. Изображения синтетические, stdlib PNG и существующие JPEG/WebP fixtures; новый SDK/Pillow не требуется.

**Основание:** [SPEC](SPEC.md), [DESIGN](DESIGN.md), [VALIDATION_PLAN](VALIDATION_PLAN.md), [B1_RESULT](B1_RESULT.md). Начальные локальные коммиты: форк `c0321032`, эксплуатация `808d04d`. Source кандидата `1810305b`; прежний контроль — старый патченный кандидат, не исходный release и не upstream main.

## Общие ограничения

- Без push/PR/переписывания Git, новых моделей, NPU, изменения сети/sshd/firewall/ядра/BIOS/питания. Секреты и sudo — только владелец; эти действия для выбранного переноса не планируются.
- Каждый запуск имеет отдельный каталог, собственную process group, loopback-порт и tmux. Только свои процессы останавливать; не использовать глобальные действия старого restart-wrapper.
- Старые исходники, бинарники, кэши и логи сохранять. Не удалять неудачные результаты. При сбое расследовать причину; новый повтор получает новый run ID и не подменяет исходный.
- Разрешены необходимые целевые сборки тестов/исправления для выполнения согласованного плана; сначала сохранить исходный кандидат и объяснить изменение. Пересборка production нужна только при подтверждённой ошибке кода.
- Все входы привязаны к source/binary/harness/model/mmproj/library SHA. Runtime пакеты проверять перед исполнением, новые зависимости не устанавливать без необходимости задачи.
- B1 остаётся совместимым с прежними параметрами/тестами. Для стадий B2/B3/C только off/mtp1, целевая модель и явный sampler. Расширение не включает DFlash2 и произвольные serve-команды.
- При тестах память сохраняет минимум 8 GiB доступной RAM, GPU usage не выше 105 GiB. Нарушение — остановка своего worker и сохранение доказательств. Это защитные границы эксперимента, не SLA.
- Нет обещания универсальной lossless/24×7 по конечному тестовому набору. Перед переключением все конкретные проверки этого плана должны иметь доказательства; нерелевантные skipped тесты не объявлять PASS.

## Принятые решения

Пользователь делегировал реализацию и дальнейшие запуски. Выбран путь расширения текущего ограниченного harness: существующий полный SDK-runner удаляет cache и содержит предположения других моделей; старый wrapper останавливает чужие движки. Отдельный второй общий API-клиент не нужен: сохраняем небольшой wire transport и повторно используем validators.

Работа идёт в существующем чистом клоне `faex2`, как в предыдущих этапах. Порог сравнения каждого запроса/фазы остаётся одновременно >5% и >3 мс. Для стабильности выбран 30-минутный непрерывный прогон после прогрева; длительность и критерии фиксируются до измерений. Самостоятельный перевод означает существующий ручной способ запуска на loopback13336, а не добавление нового systemd/autostart или открытие порта в LAN.

## Фокус ревью

1. Параллельный HTTP-запрос не должен обходить deadline или терять partial raw при отмене: отдельные процессы, отрицательные CPU-тесты.
2. B2 не должен получить PASS от флага mtp без loaded mode и реально proposed/accepted drafts: отрицательные mode/counter тесты и длинный C1.
3. Нулевой RAM-cache параметр не означает выключение: явные лимиты, проверка reuse по usage/preload, сохранённый cache при restart.
4. Reasoning-on не должен выдавать TTFT за время первого видимого текста: отдельная content timestamp; budget проверять счётчиком Responses, не длиной строки.
5. Cutover не должен останавливать посторонний процесс или затирать старую рабочую команду: snapshot/hash guard, отдельный backup, владение процессом, проверка отката.

## Задача 1. Профили и ограниченный HTTP transport

Файлы: изменить `tests/functional/faex2.py`, `test_faex2.py`, тестовый fake server; добавить `faex2_transport.py`, `test_faex2_transport.py`.

Интерфейс server: прежние `serve --config JSON --output NEWDIR` и `validate-config` сохраняются. Config получает `stage` B1/B2/B3/C, `mode` off/mtp, `sessions` 1/2/4, `context` 8192/131072, `mmproj`+SHA, `think` off/on, `reasoning_budget` 512, явные `cache_ram_bytes`, `cache_disk_bytes`, отдельный `cache_disk`, `max_request_bytes`. B1 defaults неизменны. B2: mtp1/vision/1×8192, lifetime≤1800; B3/C: 4×131072, lifetime≤7200, readiness≤240. Cache reuse разрешён только для указанного собственного каталога под run workspace. Произвольные env/argv не разрешены.

Интерфейс transport: `request --base-url LOOPBACK --request FILE --output NEWDIR --timeout SECONDS`; request JSON содержит method/path/body, по умолчанию POST chat. Сохраняет полный request/response.raw и result.json с status/text/reasoning/tools/finish/usage/metrics/первым видимым content. Ожидаемые HTTP-ошибки остаются артефактами, не маскируются. Один процесс — один запрос; hard wall≤600 с (короткие120), 16 MiB response cap. Отмена имеет отдельный ограниченный режим закрытия соединения после первого content и сохраняет partial raw.
