## 2. Пункт 1 — Бакетные HIP-графы и device-pos split-K (roadmap §3.4)

### 2.1. Что у источника (gufo-laguna, код в нашем дереве)

* **Пул графов по ширине пакета:** `StepGraph { hipGraphExec_t exec; bool failed; uint32_t steps; }`, массив `graphs[Session::kMaxVerifyRows + 1]` — 17 слотов на ширины 1..16 ([engine.cpp:333-338](../../src/models/laguna/gpu/engine.cpp)); выбор слота `graphs[min(n, kMaxVerifyRows)]` (`engine.cpp:1391`); захват на втором шаге той же ширины (`engine.cpp:1401-1419`), неудача фиксируется флагом навсегда; освобождение всех слотов в деструкторе (`engine.cpp:292-295`).
* **pos — device-параметр:** `hipMemcpyAsync(pos.get(), h_pos, ...)` из pinned-памяти — первый элемент захваченной последовательности (`engine.cpp:1271-1273`); все ядра получают указатель `pos.get() + cbank` (`engine.cpp:850-884`). При replay значение перезаписывается — сброс графа не нужен.
* **Стабильность split-K в графе:** захват разрешён только в режиме split-K (`graphable = ... && position + n >= kSplitAttnMinDepth`, `kSplitAttnMinDepth = 2048`, `engine.cpp:1396-1397`, `:57`), поэтому хост-решение о split-K внутри графа всегда истинно и сетка постоянна.

### 2.2. Что у нас

* `HipGraphDecodeExecutor` держит **один** `hipGraphExec_t instance_` + ключ `{execution_identity, workload_identity}` ([hip_graph_decode_executor.hpp:141-147](../../src/core/hip/detail/hip_graph_decode_executor.hpp)); при несовпадении — `Reset()` и перезахват. Захват есть **только для одиночного декода T=1** ([decode.cpp:78-110](../../src/models/qwen/hip/decode.cpp)); верификационные пакеты T=1..8 не захватываются вовсе.
* `pos` в графуемом пути уже device-параметр: `in_params[2] = {token_id, pos}` копируется H2D, ядра читают `*d_pos` (`decode.cpp:47-49`, `attention_decode_graph.hip:28,99,198`, `rope.hip:84`, `fused.hip:34`) — это точный аналог лагуновского паттерна.
* **Почему split-K выпадает из графа:** `ResolveQwenGraphRejections` ставит `kSplitKAttentionRequired` ([execution_policy.hpp:167-184](../../src/models/qwen/hip/execution_policy.hpp)); split-K ветка зовёт host-pos вариант `LaunchAttention` (`decode_step.cpp:180-191` → `attention_decode.hip:970-1051`), где `pos` передаётся скаляром в `QwenDecodeSplitKAttentionHalfPartialsKernel` ([attention_decode.hip:620-627](../../src/models/qwen/hip/kernels/attention_decode.hip)) — скаляры запекаются в граф.
* Буфер `d_decode_step_params` из текста roadmap **в дереве не существует** — его нужно создать; ближайший аналог — `scratch.decode.prompt_tokens` (2 слова). Благоприятно: `SelectDecodeAttentionSplitCount` возвращает только 1 или 32 (`detail/attention_policy.hpp:49-55`), т.е. «фиксированная сетка max_splits» уже обеспечена.

### 2.3. Необходимость и целесообразность

Необходимость подтверждена нашими же замерами: двухрежимная пауза очереди 27–39 мс при C4 и 315 мс на первом запросе (roadmap §2.В п.10) и потеря графов при истории > порога split-K (§1.2 п.1). Целесообразность высокая: это уже Этап 2 плана, а паттерн laguna ложится на нашу архитектуру без переделки non-split путей.

### 2.4. Объём, конфликты, риски

* **Объём:** split-K device-pos ≈ 120–180 строк (5–6 файлов); пул графов ≈ 70–120 строк (`hip_graph_decode_executor.hpp`, `decode.cpp`); захват verify-пакетов T=1..8 ≈ 200–400 новых строк (основной труд). Итого **~390–700 строк**.
* **Риски:** per-row `pos + row` корректен только для непрерывных позиций (у нас так); `hipMemcpyAsync` из pageable-памяти синхронен — нужен pinned-буфер; sparse-ветка читает хостовый `pos` и динамический пулинг — её в граф не брать (у laguna аналогичный `UpdatePooledKeys` вынесен из графа, `engine.cpp:859-870`); при T>1 меняются размеры SSM-буферов — расширять ключ графа или ограничить пул.
* **Правовая сторона:** код laguna уже в нашем дереве на тех же условиях (см. §9).

**Вердикт: ДЕЛАТЬ** в рамках Этапа 2; источник — образец, не патч.

## 3. Пункт 2 — MoE-роутинг и grouped/indirect MoE GEMM (roadmap §1.2 п.2)

### 3.1. Главная находка: у нас уже есть всё, что roadmap предлагает «проверить»

Проверка кода показала, что оба механизма из формулировки §1.2 п.2 («верификация нескольких токенов без чтения всех 256 экспертов», «grouped/indirect MoE GEMM») **уже реализованы в нашем дереве**:

* **Indirect-доступ в decode/verify:** `qfn_mmq_moe_gated_vec`/`qfn_mmq_moe_vec` ([ops/moe_vec.hpp:13-21](../../src/models/qwen/hip/ops/moe_vec.hpp)) → `moe_vector_projection` (qfn_mmq.hip.cpp:418) → `launch_moe` ([mmvq.hip.cpp:976](../../src/models/qwen38_flash_next/kernels/rocm/mmq/mmvq.hip.cpp)): двумерный grid `((rows+1)/2, experts_used)`, каждый слот читает **только свой выбранный эксперт** через индексацию `ids` (`mul_mat_vec_q_moe`, mmvq.hip.cpp:279). На токен читается 8 routed + shared + 264 строки роутера — «все 256 экспертов» не читаются нигде.
* **Группировка слотов одного эксперта:** `group_moe_slots` (mmvq.hip.cpp:563) + `launch_moe_grouped` (:805) для пакетов, `group_moe_batch` (:757, запуск в :1437) + wave64-вариант для больших. Лимиты vec-пути: `MMVQ_MAX_ROUTED_BATCH = 64` ([mmvq.hpp:4-5](../../src/models/qwen38_flash_next/kernels/rocm/mmq/mmvq.hpp)); ограничение «gated ≤ 32 used» — ассерты в mmvq.hip.cpp:1403, 1436, 1444. Весь этот слой живёт в `src/models/qwen38_flash_next/kernels/rocm/mmq/` и используется нашей 35B как библиотека (MMQ expert kernels — roadmap §1.1).
* **Grouped MoE prefill:** `QwenMoePrefill` ([moe_prefill.hpp:30-53](../../src/models/qwen/hip/moe_prefill.hpp)) → `RoutedCompactRows` (сортировка слотов по экспертам) + `RoutedF16Gemm` в `qwen35moe_prefill.cpp`; финал слит (`LaunchMoeCombineResidualAddRMSNorm`, moe.hip:433-442). Это тот же механизм, которым пользуется и gufo-laguna (`RoutedCompactRows`/`RoutedF16Gemm`, `gpu/engine.cpp:466-476`) — заимствовать в laguna нечего.
* Поправка к тексту roadmap §1.1: имени `GetMoeFfnScratch` в дереве нет; есть `QwenMoeScratch` ([executor.hpp:320-333](../../src/models/qwen/hip/executor.hpp)) и `kMoeFfnScratchRows`; изоляция буферов — `f3e8fc32`.

### 3.2. Гипотеза «размытия экспертов» при MTP2/3 — физика, не дефект кода

При T verify-токенах уникальных экспертов на слой ≤ min(8·T, 256): T=1→8, T=2→≤16, T=8→≤64 — рост чтений линеен до насыщения, это свойство MoE, а не баг. Группировка помогает только когда слоты делят одного эксперта; произойдёт ли это на реальных MTP-пакетах — вопрос телеметрии, не кода. Просадка MTP2/MTP3 на 2–4 потоках (roadmap §2.Б п.7) может иметь другие причины (когорты, кэш, планирование) — сначала измерить, потом менять код.

### 3.3. Что у других источников

* **strixite** (`moe_grouped.hip`, `moe_router.hip`): другая модель (512 экспертов, 10 used), гистограммная сортировка слотов и WMMA-тайлы ≤16 слотов; их роутер «под 512 экспертов» нашему топ-8 из 256 уступал бы. Код AGPL — запрещён к переносу (§9). Идея-кандидат — только `mtp_pick` (top-2 одним 64-байтовым копированием вместо 5 копий) — и та решается у нас средствами существующего `LaunchMoeRouterTopK`.
* **tubo dflash** (6 файлов): **0 упоминаний moe/expert** — их DFlash-драфтер плотный; для нашего Этапа 0 это значит, что перенос DFlash2 из tubo ничего бы не дал и по MoE-части.
* Наш `mmvq.hip.cpp` (`src/models/qwen38_flash_next/kernels/rocm/mmq/`, 1511 строк) — надмножество mmq-версии клонов (896 строк).

### 3.4. Вердикт

**НЕ ЗАИМСТВОВАТЬ.** Обязательного объёма — ноль. Единственный дешёвый собственный шаг: убедиться тестом/профилем, что verify-пакеты MTP2-4 идут через vec-путь (≤ `MMVQ_MAX_ROUTED_BATCH`) и, при желании, группировать чанки >8 токенов уже имеющимся `launch_moe_grouped` — и только после телеметрии уникальности экспертов на реальной нагрузке. Пункт §1.2 п.2 в roadmap стоит пометить «закрыто проверкой кода 2026-11-17».

* Сторонний замер (тот же автор кодбук, другая сборка; tubo помечает «not our measurement», N47): turbo6/turbo6 (K и V оба turbo6) KLD 5,0–5,6e-4 против q8_0/q8_0 2,5–3,6e-4 — `Q8_0` численно точнее, turbo6 компактнее (при 262K на их модели: turbo6 6,58 ГБ, q8_0 9,13 ГБ, fp16 17,18 ГБ).

### 5.3. Что уже сделано у tubo — и уроки для нашего §3.2

Tubo реализовал **ровно ту схему, которую предлагает наш §3.2**, и оставил три готовых урока:

1. **Enum дописывать в конец.** В persisted-снапшоте хранится числовое значение энума: `kFp32=0, kFp16=1, kTurbo4=2...` дописаны, не вставлены; precision-bound в `arena.cpp` поднят до последнего энума (иначе свой же билд отвергнет свой снапшот) (`execution_policy.hpp:11-49` клона tubo).
2. **Смешанный кэш — таблица по слоям,** а не один энум: `QwenKvLayerFormat` на плоскость (K/V отдельного слоя), потому что «последние N слоёв turbo4, остальные fp16» не выражается целым энумом.
3. **Одна формула смещения на оба направления.** `QwenKvHeadBlockOffset` — единственное место арифметики, им пользуются и writer, и reader (`kv_read.hpp:1-40` клона tubo): «две формулы смещения не поднимают ошибку — они молча возвращают чужую голову». Плюс CPU-оракул кодека: байтовая идентичность host/device.

### 5.4. Наша сторона и объём

* Раскладка: `QwenKvCacheStorage` содержит только `kFp32/kFp16`; `arena.cpp` выбирает размер элемента плоскости по `kv_storage == kFp16 ? uint16_t : float` (строка 176), а precision-bound, который придётся поднимать, — строки 253–256. Геометрия 35B: head_dim 256, 2 KV-головы → 20 480 Б/токен (10 слоёв). `Q8_0` → 10 880 Б/токен (−4,7 ГБ на 4×128K); turbo6 (2 блока по 98 Б на голову-плоскость) → 784 Б/слой/токен = 7 840 Б/токен (−6,6 ГБ на 4×128K).
* Чтение: `pos` в split-K ядре — скаляр (`attention_decode.hip:620-627`); для Q8_0/turbo чтение требует деквантования в `QwenDecodeSplitKAttentionHalfPartialsKernel` (план §3.2 уже это фиксирует). Tubo расширял это же семейство ядер маленькими совместимыми правками (kVSkip, Tile — +81/−17 в `attention_decode.hip`) — семейство расширяемо, но у нас своя история файла (наш `6bcf0c3b`), поэтому **перенос — по формату и математике (`turbo4_kv_write`/`kv_dequant`, `kv_allocation`), встраивание — в наши ядра**.
* Оценка объёма: `Q8_0` — квантование в эпилоге KV-write + деквантование в split-K/verify-ядрах + enum/снапшот-идентичность ≈ **300–500 строк**; `kTurbo6` — ещё **~800–1200 строк** (кодбук-кодек + оракул + ядра) — только вторым шагом.

### 5.5. Необходимость, целесообразность

* **Необходимость — условная.** При текущем профиле 4×128K память не дефицит (55,2 ГиБ на 4×262K исторически работало); выигрыш скорости decode ограничен долей KV-чтения (на длинной истории — доминирует). Реальная боль появляется при 4×262K и при 8+ сеансах.
* **Целесообразность:** `Q8_0` — да (Этап 3 уже запланирован; Q6dense независимо подтвердил «8-bit KV copy: unchanged judge scores»); `turbo6` — только после `Q8_0` и при реальной потребности в >262K (потолок 4×262K и так достигается Q8_0).
* **Критерии приёмки** из NEXT_STAGE_SPEC §8/§10 переносим без изменений: отдельная identity (fingerprint), сутки наблюдения на 4×131072 до 262K, CPU-оракул, sparse+квант вместе не включать.

**Вердикт: ДЕЛАТЬ `Q8_0` (Этап 3) с тремя уроками tubo; `kTurbo6` — опционально вторым шагом.**

## 6. Пункт 5 — `Q6_K` dense + `UD-Q4_K_XL` experts и формат `.ghalo` (roadmap §1.2 п.5, §3.1, Этап 4)

### 6.1. Что такое Q6dense на самом деле

Форк NinjaPear содержит **2 собственных коммита**; «Q6dense» — не код движка, а **рецепт квантования весов**: `llama-quantize --imatrix imatrix_unsloth.gguf_file --tensor-type-file q6dense.types <unsloth BF16 GGUF, rev 5bc3e238> <out> Q4_K_M 16` (их README «Producing Q6dense»; базовый тип Q4_K_M, каждый тензор задан явно). Схема: trunk dense → `Q6_K`, роутируемые эксперты → как в `UD-Q4_K_XL`, эмбеддинги и dense-часть MTP → `Q8_0`.

### 6.2. Совместимость с нашим движком

Наш загрузчик уже принимает все нужные типы по ролям: `kEmbedding` — F32/BF16/Q8_0/Q4_K/Q5_K/Q6_K/… ([weights.cpp:66-76](../../src/models/qwen/weights.cpp)), `kProjection` — все K-кванты (стр. 83-90), роутер — только FP32-семейство (`SupportsMoeRouterType`, ограничение `355b1d86`). Значит, GGUF по рецепту Q6dense **должен загрузиться без правок движка** — но это надо подтвердить на реальном файле (роль MTP-норм `nextn.*` требует F32; содержимое `q6dense.types` публикуется вместе с весами на HuggingFace и в клоне отсутствует).

### 6.3. Качество и скорость (замеры Q6dense, октябрь 2026; не наши)

* Паритет с llama.cpp на том же GGUF: top-1 **443/445**, KL mean 0,0020 (их QUALITY.md).
* Судейская оценка против **нашего текущего формата** UD-Q4_K_XL на одинаковых страницах: products **7,25 vs 7,25**, bios **7,62 vs 7,62** — качество не хуже.
* Скорость (их движок + их ядра, gfx1151 128 ГБ): MTP tg 8K — 101 ток/с (смешанный текст); AR tg 8K — 67 ток/с; prefill 8K — 2821 ток/с. Веса 22,5 ГиБ.
* Готовые отрицательные результаты (их EXPERIMENTS.md): **Q5_K dense — отклонён** («no speed gain»); bartowski Q4_K_M dense — отклонён (медленнее); in-kernel MoE grouping — отклонён («slower»).

### 6.4. Необходимость, целесообразность, объём

* **Необходимость:** низкая/средняя — наш формат уже даёт равное судейское качество; выигрыш Q6_K dense — точность роутера/dense и небольшой запас до потолка ПСП (roadmap §1.2 п.5). Самостоятельной боли нет.
* **Целесообразность:** высокая как **дешёвый изолированный эксперимент**: не требует кода движка, только скачать unsloth BF16 (два шарда), requantize по рецепту и прогнать наши приёмки (Q1 + hermes_synth + судейская выборка). Важно: квантовать нужно **из BF16-исходника** — переквантование нашего UD-Q4_K_XL вверх бессмысленно.
* **Объём:** 0 строк кода движка; 1 вечер стенда на прогон. Риск — только время стенда.
* **`.ghalo` (§3.1):** собственный формат-образ сейчас **не нужен**: Q6dense показывает, что стандартный GGUF + рецепт даёт результат без нового контейнера; выравнивание/кэш-перепаковка имеет смысл только после того, как профиль узких мест подтвердит, что упираемся в раскладку. Примечание: раскладка `TensorEntry` в roadmap уже выровнена по uint64 правкой `26904442`; при возврате к теме — держать инвариант «`data_offset` кратен 128 байтам» и не вводить скрытого паддинга.

**Вердикт: ПОПРОБОВАТЬ рецепт Q6dense (дёшево, изолированно, в Этап 4); `.ghalo` — ОТЛОЖИТЬ.**

### 6.5. strixite: только идеи, ни одной строки (AGPL)

Изучение движка дало четыре дизайн-рецепта, применимых к нашему Этапу 4 и §3.2 (код переносить запрещено — AGPL-3.0, см. §9):

1. **WMMA-тайлинг GEMM:** K-шаг `kWmmaKC = 64` при LDS-строке `kWmmaLd = 72` (64+8 — паддинг против bank conflicts), «коды — в LDS, масштабы — в FP32-аккумулятор» по группам 32/64/128. Сам intrinsic `v_wmma_f32_16x16x16_bf16` у нас уже используется (`mmq/mma.hpp:796-1012`) — заимствовать примитив не нужно, нужен только тайлинг.
2. **Выравнивание плотных форматов:** их плотный Q6 требует `K % 64 = 0`, чтобы плоскости строки оставались 16-байт выровненными — это и есть обоснование правила «`data_offset` кратен 128 байтам» из §3.1. Их контейнер `strixw` (v4: заголовок 128 байт, выравнивание тензора 4096, piecewise 64-битный hash) подтверждает саму схему `.ghalo`, но их код не копируется.
3. **kv8 — рецепт для квантованного KV:** K — асимметричные 8 бит **по каналам** на группу 32 значений (после norm+RoPE у K поканальные сдвиги — −42 % ошибки против симметричных блоков), V — по блокам 32; «хвост» непокрытых строк живёт в активной точности; `kv8_exact_from(p)` — запрос видит ровно то, что видел бы при потоковом декоде. Для нашего `Q8_0`-этапа это аргумент рассмотреть **поканальную** шкалу K вместо чисто блочной.
4. **Схема точности весов подтверждена их замерами:** эксперты 4-бит (группы 128), весь «каждый токен читаемый» путь 8-бит, embedding/router BF16 — тот же принцип, что наш план «Q6_K dense + Q4_K experts + FP32 router».
