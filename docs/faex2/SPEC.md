# Спецификация Gufo FAEX2

Дата: 2026-11-09. Зафиксированы заявленные владельцем цели и уже принятые рабочие ограничения. Неустановленные пороги явно оставлены открытыми; этот документ не объявляет завершённую приёмку.

## Назначение

Быстрый и надёжный локальный inference backend для семейного чата. У каждого пользователя отдельный агент в отдельной ВМ; агенты обращаются к общему экземпляру модели через API. Основной язык — русский. Частые задачи: диалог, поиск в интернете через инструменты агента, объяснение школьных заданий подростку, чтение изображений; программирование — вторичный сценарий.

Приоритеты: **сохранность доступа и данных → корректность/стабильность → скорость → экспериментальные возможности**. Пользователь хочет максимум скорости без потери качества, а не максимальное число tok/s на одном удобном промпте.

## Границы поддержки

| Область | Контракт проекта |
|---|---|
| Модель | Qwen3.6-35B-A3B; текущие испытанные веса UD-Q4_K_XL GGUF, встроенная MTP-голова, mmproj BF16 |
| Устройство | FEVM FAEX2, 128 ГБ RAM, AMD Ryzen AI Max+ PRO 495; целевой GPU gfx1151 |
| ОС/вычисления | Linux x86-64; действующий стенд CachyOS, GPU HIP. Проверенные зависимости записываются с baseline, rolling-обновления не считаются автоматически совместимыми |
| API | OpenAI-совместимый используемый агентами интерфейс: текст, streaming, изображения, tool calls. Совместимость с конкретными клиентами доказывается тестами, не названием протокола |
| Нагрузка | Проверяем 1, 2 и 4 одновременно выполняющихся диалога. Более широкая нагрузка вне текущей квалификации |
| Контекст | Рабочий тестовый пресет 4 × 131072; отдельно испытана память 4 × 262144. Это не гарантия интерактивной задержки при полном контексте всех слотов |
| Спекуляция | Рабочий кандидат MTP 1; DFlash2 доступен как эксперимент. При невыгодной спекуляции допустим корректный target-only путь |
| Зрение | Изображения с соответствующим проектором этой модели; новые форматы/размеры и мультиизображения расширяют тестовую матрицу |
| NPU | Будущее исследование. Не условие первого выпуска и не подтверждённое ускорение/качество на этом стенде |

Иные модели в исходном Gufo не удаляем ради специализации. Они вне обещаний поддержки форка; изменения общего кода всё равно требуют разумных регрессионных проверок.

## Разделение обязанностей

**Движок:** загрузка весов, токенизация и шаблоны, prefill/decode, выборка/верификация черновика, vision encoder, KV/prompt cache, планирование запросов, API, метрики и корректные ошибки.

**Агенты/приложения в ВМ:** поиск и браузер, вызов инструментов, семейная память, персональные системные инструкции, политика доступа, педагогический стиль и пользовательский интерфейс. Не встраивать семейные данные, поисковые ключи и школьные инструкции в HIP/C++ движка.

**Эксплуатация:** сеть, firewall, SSH, BIOS, ядро, веса на диске, systemd, секреты, реальный deploy/rollback — в отдельном непубличном проекте машины.

## Приёмка изменений

### Корректность и качество — обязательный барьер

- Сравнивать кандидата и контроль на одинаковых весах, template/tokenizer, sampler и условиях. Смена квантования — отдельный эксперимент, не бесплатная оптимизация.
- Для спекуляции проверить принятие/отклонение, residual sampling, согласование состояния/кэшей, переходы нагрузки, EOS/tool tokens и ненулевую temperature. Равные seed при разных реализациях сами по себе не доказывают/не опровергают равенство распределений.
- Для численных ядер — CPU/надёжный reference с обоснованными допусками и end-to-end задачи. Косинус эмбеддингов сам по себе недостаточен.
- Набор: русские инструкции/пересказ, школьная математика и объяснения, фотографии текста/формул/таблиц, tool name/arguments/results, длинная история, повторный префикс, независимость сессий. Добавить обезличенные фикстуры, не публиковать семейные материалы.
- Пустой/повреждённый ответ, неверная маршрутизация/смешивание сессий или поломка инструментов не компенсируются большей скоростью.
- «Без потери качества» — требование и проверяемая гипотеза. Конечный тестовый набор не доказывает универсальное отсутствие регрессий; ограничения писать явно.

### Скорость

Измерять prefill, decode на поток и суммарно, TTFT, время до содержательного ответа и полного завершения, vision отдельно, очередь и хвосты задержек при 1/2/4 запросах. Разделять холодный/тёплый кэш и рассуждения/видимый ответ. Сохранять неуспешные запросы и условия, не выбирать только удачные прогоны.

Исторический критерий выбора режима 2026-11-09: на прозе при 2 и 4 диалогах, greedy и sampling, скорость не ниже `off` более чем на 3%; затем максимум однопоточной прозы, при близких результатах код вторичен. Это критерий того эксперимента, а не универсальный допуск потери качества и не замена метрикам задержек.

Абсолютные целевые p95 TTFT/время ответа и допустимый memory budget для production **ещё не согласованы**. Не назначать их задним числом по получившимся результатам.

### Надёжность и выпуск

- Проверить длительную работу, отмену/обрыв клиента, таймауты, ошибки, отсутствие неконтролируемого роста памяти, независимость сессий и восстановление.
- Каждый candidate привязан к точному SHA, весам и их хешам, toolchain, параметрам сборки/запуска, тестовому harness и истории кэша.
- Раздельные тестовый и рабочий артефакты; прежний рабочий артефакт сохраняется. Переключение и откат проверяются без пересборки по памяти.
- Git-тег указывает на код, но не заменяет бинарник и manifest окружения. Нынешний baseline ещё не объявлен production-релизом.

## Не-цели ближайшего этапа

- Универсальная поддержка множества моделей/устройств и удаление общего кода ради неё.
- Автоматическое обновление vendor/upstream по календарю без проверки.
- Включение NPU, разгон/даунвольт, смена BIOS/ядра ради оформления проекта.
- Слияние всех изменений в один большой внешний PR.
- Полная копия эксплуатационного репозитория в публичном форке.

## Открытые решения

1. Полный воспроизводимый manifest baseline и перенос минимального обезличенного harness.
2. Объём русского/vision/tool regression-набора и пороги задержек под семейную нагрузку.
3. Политика per-request reasoning budget; текущий исследованный лимит серверный и общий.
4. Квалификация корректности sampled-MTP и новых форм/размеров изображений.
5. Формат рабочего артефакта, процедура выпуска и защиты GitHub-ветки.
6. Только после этого — конкретная задача NPU и подтверждение её полезности end-to-end.
